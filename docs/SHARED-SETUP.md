# 두 사람이 함께 사용하는 준비 공간

GitHub Pages는 화면을 배포하고, 로그인과 공유 데이터는 Supabase에 보관합니다. 연결하지 않은 상태에서는 현재 기기의 브라우저에 자동 저장됩니다. **기기 자동 저장과 공유 저장은 별개입니다.** 공유 공간에 저장한 내용을 다른 기기에서 가져와 이어서 편집합니다.

## 최초 설정

1. [Supabase](https://supabase.com/dashboard)에서 두 분이 사용할 프로젝트를 하나 만듭니다.
2. 프로젝트 **SQL Editor**에서 저장소의 [`supabase/setup.sql`](../supabase/setup.sql) 전체를 실행합니다. 이미 실행한 프로젝트에서 다시 실행해도 기존 계획은 삭제하지 않습니다.
3. **Authentication → Providers / Sign In**에서 Email 로그인을 사용하도록 설정합니다. 두 분의 개별 이메일로 로그인합니다.
4. **Authentication → URL Configuration**의 Site URL과 Redirect URLs에 실제 GitHub Pages 주소를 등록합니다. 프로젝트 사이트라면 `https://GITHUB_ID.github.io/REPOSITORY/`처럼 저장소 경로와 끝의 `/`까지 포함합니다. 로컬 확인을 한다면 실제 개발 서버 주소도 Redirect URLs에 별도로 추가합니다.
5. **Connect** 또는 **Settings → API Keys**에서 Project URL과 **Publishable key**를 복사합니다. URL은 `https://PROJECT_REF.supabase.co` 형식입니다. `sb_publishable_...` 공개 키를 권장하며 기존 `anon` 키도 지원합니다. **Secret key / service_role 키는 사용하지 않습니다.**
6. 플랫폼의 공유 설정에서 URL과 공개 키를 저장합니다. 다른 휴대폰·PC에도 같은 값을 한 번씩 입력합니다. 설정은 현재 브라우저에 저장됩니다.
7. 이메일 로그인 링크를 요청하고 메일에서 링크를 엽니다. 각 기기에서는 해당 기기의 브라우저로 로그인을 진행합니다. 메일 앱의 내장 브라우저가 열렸다면 플랫폼을 사용할 Safari/Chrome 등 같은 브라우저에서 링크를 여세요.

이메일은 Supabase의 발송 정책과 사용량 제한을 따릅니다. 기본 발송 서비스로 상대방 이메일에 메일이 가지 않으면 **Authentication → SMTP Settings**에 발송 서비스를 연결하세요. 기본 서비스는 프로젝트 팀 이메일 등 수신 대상을 제한할 수 있습니다. [Supabase SMTP 설정 안내](https://supabase.com/docs/guides/auth/auth-smtp)를 참고하세요.

## 초대와 함께 편집

1. 한 분이 현재 작성한 계획으로 **공유 공간 만들기**를 실행합니다.
2. 공간을 만든 분이 초대 코드를 생성해 상대방에게 직접 전달합니다. 코드는 7일 동안 유효하고, 상대방이 참가하면 소모됩니다. 공유 공간은 두 사람까지 참여할 수 있습니다.
3. 상대방은 같은 Supabase 프로젝트 설정을 입력하고 본인의 이메일로 로그인한 뒤 코드를 입력해 참가합니다.
4. 기존 공간은 로그인 후 목록에서 선택해 가져올 수 있습니다. 다른 기기에서 처음 연결할 때 로컬에 중요한 내용이 있다면 JSON 백업을 먼저 내려받으세요.
5. 편집을 시작하기 전에 공유 공간의 최신 내용을 가져오고, 편집이 끝나면 **공유 저장**을 누릅니다. 공유 저장이 성공해야 상대방도 변경 내용을 가져올 수 있습니다.

두 분이 같은 버전에서 동시에 편집하면 먼저 저장한 내용만 반영됩니다. 두 번째 저장은 충돌 안내와 함께 거부되며 상대방의 내용을 덮어쓰지 않습니다. 이때 **내 기기의 내용을 JSON으로 백업 → 최신 공유 내용을 가져오기 → 필요한 수정 다시 적용 → 공유 저장** 순서로 정리합니다. 현재 버전은 항목별 자동 병합이나 실시간 공동 커서를 제공하지 않습니다.

## 저장과 접근 범위

- 준비 계획은 `wedding_workspaces`에 JSON으로 저장하며, 저장할 때마다 `revision`이 증가합니다. 백엔드에서 예상 revision과 일치할 때만 한 번에 수정합니다.
- 이메일로 로그인한 공간 참여자만 계획을 읽고 저장할 수 있습니다. URL이나 공개 키만 아는 사람은 준비 데이터를 읽을 수 없습니다.
- 직접 테이블 수정 권한은 열지 않습니다. 멤버 추가, 초대 생성, 저장은 로그인·멤버 자격을 검사하는 RPC만 사용합니다. RLS는 참여자의 읽기 범위를 제한합니다.
- 초대 코드는 공간을 만든 분만 확인·재발급할 수 있습니다. 새 코드로 재발급하면 기존 코드는 무효가 됩니다. 코드는 상대방에게만 전달하세요.
- 계정 세션과 로컬 계획이 브라우저에 남습니다. 개인 기기에서 사용하고, 공용 기기에서는 사용 후 로그아웃한 뒤 브라우저 사이트 데이터를 지우세요. 정기적인 JSON 백업을 권장합니다.
- 파일이나 사진을 공유 저장소에 업로드하지 않습니다. 계획 JSON의 최대 크기는 5 MB입니다.
- Supabase 계정과 프로젝트는 사용자가 관리합니다. 프로젝트 일시 중지, 네트워크 오류, 인증 만료 중에는 로컬 편집과 JSON 백업을 사용할 수 있고, 공유 저장은 연결을 복구한 뒤 다시 실행합니다.

## 연결 확인

처음 연결한 뒤 임시 기록 한 개로 다음을 확인하세요.

1. 첫 기기에서 공간 생성과 공유 저장이 성공합니다.
2. 두 번째 이메일 계정이 초대 코드로 참가해 같은 기록을 가져옵니다.
3. 두 번째 기기에서 기록을 수정하고 공유 저장하면 첫 기기에서 변경 내용을 가져올 수 있습니다.
4. 양쪽에서 같은 버전을 가져온 뒤 각각 편집하여 순서대로 저장하면, 나중 저장에 충돌 안내가 나옵니다.
5. 로그아웃한 창이나 초대받지 않은 계정에서는 공간 내용을 읽을 수 없습니다.

SQL은 PostgreSQL 기반 PGlite에서 재실행, 참여자/비참여자/비로그인 읽기 권한, 직접 수정 거부, 초대 재발급·사용 후 무효화, 2인 제한, 오래된 revision 저장 거부를 검증했습니다. 실제 Supabase 프로젝트와 이메일 발송은 별도 계정 설정 후 위 절차로 확인해야 합니다.

## 구현 참고

- 브라우저용 Supabase SDK가 이메일 magic link의 세션 생성, URL 토큰 정리와 토큰 갱신을 처리합니다. 정적 호스팅을 위해 implicit 인증 흐름을 사용합니다. [이메일 로그인 문서](https://supabase.com/docs/guides/auth/auth-email-passwordless)
- 공개 키는 브라우저에서 사용할 수 있지만 서비스 비밀 키는 사용할 수 없습니다. 실제 데이터 접근은 로그인과 RLS로 결정합니다. [API 키 문서](https://supabase.com/docs/guides/getting-started/api-keys)
- 권한을 사용하는 함수는 비공개 `owol_private` 스키마에 두고 `search_path`를 고정했습니다. Supabase 설정의 Exposed schemas에 이 스키마를 추가하지 마세요. [RLS 문서](https://supabase.com/docs/guides/database/postgres/row-level-security), [함수 권한 문서](https://supabase.com/docs/guides/database/functions)
